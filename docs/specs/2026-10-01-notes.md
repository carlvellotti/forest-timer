Starting line: "A pomodoro timer that grows a forest."

Already settled in idea.md, DESIGN.md and docs/stack.md (not re-asked): 25-minute sessions only; a finished session grows one tree; giving up (including closing the tab halfway) is recorded but adds no tree; one screen with the timer above and the forest below; Start button and a quiet "Give up" link; saved in this browser's storage.

## Q6. If you reload the page mid-session (on purpose, by accident, or because the browser crashes), is that a give-up, or does the session pick back up?

Recommended: pick back up. The app saves when you pressed Start; come back before 25 minutes and it carries on; come back after and it's a give-up.

> reload can pick back up, that's fine. but closing the tab is still giving up. like if i start at 9:00 and close the tab at 9:10, no tree

## Q6b. Rule check: reload vs close vs crash

Fact looked up: a page can't tell a reload from a close while closing; it only learns on its next start ("I was reloaded" vs opened fresh).

Proposed rule:
- Reload mid-session: the session carries on (start 9:00, reload 9:10 → 15:00 left).
- Reload after the 25 minutes would have ended: give-up (start 9:00, reload 9:40 → no tree).
- Close the tab or browser mid-session, open the app later: give-up (start 9:00, close 9:10 → no tree), recorded next time the app opens.
- Browser crash: can't be told apart from a close, so it's a give-up.

Recommended: accept the crash case as a give-up.

> yep that matches. crash counting as giving up is fine

ADR written: docs/adr/0001-reload-resumes-close-gives-up.md

## Q13. What happens if you open Forest Timer in a second tab while a session is running in the first?

Problem found: under the Q6b rule, opening the app fresh mid-session counts as a give-up, so a second tab would kill a session still running in the first.

Recommended: one tab at a time. The second tab sees another tab is open and shows only a muted line, "Forest Timer is open in another tab.", with no timer and no buttons. The first tab carries on. Closing the second tab does nothing.

> oh good catch. one tab at a time

## Q14. If your laptop goes to sleep mid-session (the lid closes, but the tab stays open), what happens when it wakes up?

Recommended: the clock keeps running. The timer always counts from when Start was pressed (start 9:00, lid shut 9:10, open 9:15 → 10:00 left). Wake after 9:25 → finished: tree and chime on wake.

> clock keeps running. if it finishes while asleep i get the tree, it's rare enough

## Q15. While a session is running, what's on the screen besides the timer?

Recommended: two states. Ready: timer reads 25:00, Start button under it, no Give up link. Running: timer counts down (24:59, 24:58…), Start disappears, only the quiet Give up link under it. The forest stays visible below the line in both.

> yep that matches

# Spec assumptions, decided (2026-10-01)

## A11. Should Forest Timer work in a phone's browser, not just on a laptop?

Recommended: yes, phones too.

> phones too, i'd def use it on my phone

## A1 + A2. What happens when a reload comes after the 25 minutes are up?

Problem: on phones the browser often reloads a background tab by itself (start 9:00, lock phone, open browser 9:40 → reload). Rule 5 (give-up) clashes with rule 9 (sleep: clock keeps running, tree if it finished). The app can't tell your reload from the phone's.
Recommended: change rule 5 so a reload after 25 minutes counts as finished (tree and chime). Close and crash still give up.

> makes sense, change it to finished

**Rule 5 changed: a reload after 25 minutes counts as finished.** ADR 0001 amended.

## A3. Crash restore: some browsers bring a crashed tab back as a reload. Accept that the reload rules then apply?

Recommended: accept it. Rule 7 gets an exception: if the browser brings the tab back as a reload, rules 4 and 5 apply.

> accept it

## A4. Hitting zero mid-confirmation: the timer reaches 0:00 while "Give up? No tree this time." is showing.

Recommended: the session finishes with the tree and chime; the question disappears. (My example said "at 24:58"; corrected to 0:02 left.)

> yes finishes with a tree. but 24:58 is right at the start isn't it? you mean like 0:02 left

## A5. The second tab after the first closes: stay as it is until reloaded, or switch by itself?

Recommended: stays until you reload it, then opens normally. Closing the first tab mid-session is still a give-up (rule 6), recorded when the second tab reloads.

> stays until i reload

Follow-on made precise in the spec: rule 4's "reload" means a reload of the tab the session started in, so reloading the second tab doesn't pick up the first tab's session.

## A6. "Ended" for a close: is "to within a few seconds" fine, or does it need to be exact?

Recommended: while a session runs, the app notes the time every few seconds; the last noted time is "ended" for a close or crash.

Recommended: stays on the newest tree across visits.
